# Refactor Phase 1

Date: October 5, 2026  
Baseline: Boxer `branch-test-800-lib` at `21808021`; DOSBox-Staging submodule `a037da71` (`boxer-compat-localtest810`).

## Status

The Xcode project now has a separate `DOSBoxStaging` static-library target that produces `libDOSBoxStaging.a`. Boxer links that product, and the FreeDOS keyboard resources are copied into the app bundle.

The target currently compiles the DOSBox-Staging sources through an explicit Xcode `PBXSourcesBuildPhase`. It is not generated by CMake or Meson. Updating the DOSBox-Staging submodule changes the source tree, but does not automatically update the Xcode source membership; newly added or renamed source files must be reflected in the project.

## Verification

- `DOSBoxStaging` is registered as an Xcode target with product `libDOSBoxStaging.a`.
- Boxer links `libDOSBoxStaging.a`.
- `DOSBox-Staging/contrib/resources/freedos-keyboard` is included in Boxer’s resources.
- The project builds successfully in Debug with Xcode.
- The DOSBox source phase currently contains a duplicate `dos_memory.cpp` entry and should be deduplicated.
- The Boxer target should explicitly depend on `DOSBoxStaging` so a clean build always compiles the library before linking Boxer.

## Build/update model

`libDOSBoxStaging.a` is an intermediate product generated by Xcode in DerivedData. It is rebuilt when the `DOSBoxStaging` target’s inputs or build settings require it; it is not committed to the repository. After a DOSBox-Staging update, review the target’s source membership and resource paths, then rebuild the dependent Boxer target.

## Remaining project work

The target-dependency relationship and duplicate source entry should be corrected in Xcode’s project editor, then committed separately from the source and configuration fixes. This avoids relying on hand-edited project-file structure while Xcode is open.
